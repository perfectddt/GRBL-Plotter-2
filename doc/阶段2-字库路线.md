# 阶段2 字库路线（2026-10-06 决策）

2026-11-08 更新：按用户要求重新验证 CNCDraw 格式资料，实测 70 个本机 GFont 的字形 ZIP 可直接读取，旧版“字形载荷全部加密”的判断已被修正。此次跳过加密元数据，保留本机使用、字体数据不入仓库的约定。详见[本机字库导入与权重混写](本机字库导入与权重混写-20261108.md)。

## 1. 决策背景与结论

- 原软件 `gcodeFonts/` 带 71 种 `.gfont` 单线手写字库（田英章楷书、徐静蕾、方正兰亭超细黑等）。实测结论：**文件为厂商加密**——除 8 字节头外载荷全程高熵，2.5MB 文件内坐标指令模式出现 0 次（明文 G-code 对照组 18KB 内 689 次），各种记录容器假设均无法走查到文件尾；软件自带 `KvenjoyEncrypt.dll` 加密模块，主程序 `core` 同样整体加密。
- 按交接约定**不破解加密模块**。且这批字体混有方正、汉仪、华康等**商业字库**，字体版权独立于软件厂商，"免费下载的安装包"不等于字库授权免费。绕过保护的动作本身与商用与否无关，不做。
- 用户决策（2026-10-06）：放弃 `.gfont`，改走开放授权数据。原软件的"打字→导出明文 G-code"通道仍可作为字形摄取的补充手段（用软件自身功能，不涉破解），按需摄取。
- **结论：路线 A（开放笔画中心线数据，先做）→ 路线 B（免费 TTF 骨架提取，其次）。两条路线产物统一为"字形字库包 JSON"（fontpack），经同一加载链进入现有排版/生成代码。**

## 2. 路线 A：HanziWriter 笔顺中心线数据（本轮开发）

- 数据源：`hanzi-writer-data@2.0.1`（GitHub `skishore/makemeahanzi` 的 npm 发行包；本机 GitHub raw 直连被重置，经 npmmirror 整包下载）。共 9574 个有效字符，每字含 `strokes`（轮廓 SVG 路径）与 `medians`（**每笔一条中位折线，按真实笔顺排序**）。中位线即笔画骨架，正合笔式写字机"走中心线"的需求，且笔顺有序让机器像人一样一笔一画写。
- 授权：**Arphic Public License**（包内 `ARPHICPL.TXT`），允许使用/修改/再分发，需保留署名与许可文本。仓库内副本：`GRBL-Plotter/AutoWriter/Fonts/LICENSE-arphic.txt`；字库包 JSON 内亦写入 source/license 字段。
- 坐标系与定标（实测全库 9574 字统计）：
  - 源坐标系：em 框 1024 单位，Y 向上，**基线 y=0**；墨高 P50=813 / P90=886 / max=963 单位，墨底最深 −96（下垂区），墨顶最高 885。与 hanzi-writer 的 900 可视框变换吻合。
  - 定标常数：**字面高 880 单位 → BodySizeMm 10mm**（scale = 10/880 = 0.0113636 mm/单位）；**基线 y=0 → baselineMm 1.0**（与内置字形 1..11 字身完全同构，全高字顶恰落在 11mm）；X 居中偏移 (12 − 1024×scale)/2 ≈ 0.18mm；步进宽 CJK = EmSizeMm 12mm、空格 = 6mm（沿用内置约定）。
  - 效果：全高字（木/中/金类）≈ 9.7~10mm 高，稀疏字（王 610 → ≈6.9mm、一 62 → ≈0.7mm 细横）按真实比例——这是排版学上正确的做法，内置"工王一"是把每个字都撑满 10mm 的示意图规格，两者不可比高。
- 产物：
  - `scripts/generate-stage2-fontpack.py`：离线生成脚本（确定性输出、键排序、坐标 3 位小数），支持 `--chars-file` 扩包与 `--all`（全库 9574 字）。
  - `GRBL-Plotter/AutoWriter/Fonts/hanziwriter-pilot.fontpack.json`：试点字库包（常用字 520 字，含纸面样本用字 永和国工王一二三）。
  - `GRBL-Plotter/AutoWriter/Services/GlyphFontPackService.cs`：加载器（DataContractJsonSerializer 类型化契约，沿用 MachineProfile 惯例；加载即校验：schema 版本、笔画点数为偶、数值有限、坐标在 em 框内容差）。
  - 解析链：`ResolveWithFallback` = **字库包 → BuiltinGlyphLibrary → 报缺字**（大声拒绝，不静默跳过）。
  - 测试：`scripts/test-stage2-fontpack.ps1`（离线断言）；样本：`scripts/generate-stage2-fontpack-sample.ps1` → `artifacts/stage2/stage2-fontpack-sample-6mm.nc`（纸面验收用）。
- 已知边界（不得据此宣称手写体效果）：中位线是均匀骨架，无起收笔锋与粗细变化；与原厂手写体的"字感"有差异。生僻字不在试点包内的会大声报缺字，扩包重跑脚本即可。

## 3. 路线 B：TTF 骨架提取（2026-10-06 晚已完成 v1）

- 流程（`scripts/generate-stage2-fontpack-ttf.py`）：PIL/FreeType 按字栅格化（em 400px）→ 3×3 形态学闭运算 → numpy 向量化 Zhang-Suen 骨架化 → 迭代剪除 ≤12px 毛刺 → 骨架图提取（deg≠2 为节点、deg-2 链为边）→ **交叉簇收缩 + 出入方向配对合并 + BFS 桥接**（交叉处不碎裂）→ Douglas-Peucker 简化 → **笔画级端点缝合**（间距 ≤24px 且方向顺的相邻片段拼回一笔）→ 启发式笔序（横笔左→右、竖笔上→下）→ 与路线 A 相同的 fontpack 格式与定标（cap 参考字中位墨高 → 10mm、基线 → 1mm）。
- 依赖：python + `numpy` `fonttools` `pillow`（`pip install -i https://mirrors.aliyun.com/pypi/simple/ numpy fonttools pillow`）。
- 授权边界：默认字体为 Windows 自带楷体 `simkai.ttf`（中易字库，随 Windows 授权）——**衍生数据仅限本机使用，字库包只写到 artifacts/ 不入仓库**；换授权干净的字体（全字库楷体 TW-Kai[政府开放授权]、思源[OFL]，`--font` 指定）生成才可入库。生成脚本与测试入库，数据不入。
- 离线套件：`scripts/test-stage2-fontpack-ttf.ps1`（--limit 24 现场生成小包 → 生产加载器 → 22 断言：几何、解析链、混排、端到端连续笔控），全 PASS。
- 已知质量边界（诚实记录，不得宣称"手写体效果"）：
  - **笔序是启发式**（横左→右、竖上→下、整体上→下左→右），不是路线 A 的真实笔顺；
  - **楷体笔锋（顿笔/回锋）在骨架上留下卷曲**，交叉/端部仍会多出 1~3 笔（王 7 笔 vs 真 4 笔、永 17 笔）；打印风格字体（黑体/宋体）骨架会干净得多；
  - 对交叉密集的字（国、事）交叉簇合并已工作（竖笔贯通、外框成环），但个别交叉仍可能断成两段——形状完整、只是多一次提笔。
- 质量演进候选（未做）：矢量轮廓直接求中轴线（免栅格化）、交叉簇配对阈值自适应、TW-Kai 下载重试。

## 4. 数据流

```
数据源(hanzi-writer-data / TTF)
  │ scripts/generate-stage2-fontpack.py（路线B脚本后补）
  ▼
Fonts/*.fontpack.json（mm 坐标、em 12mm、基线 1mm）
  │ GlyphFontPackService.LoadFromFile
  ▼
TextLayoutService.Layout(文本, ResolveWithFallback, 字距, 行距, 行高, 字号缩放)
  ▼
WritingProgramService.Generate（连续笔控 G-code）→ 纸面验收
```

## 5. 复现步骤（数据获取）

1. `curl -o hanzi-writer-data.tgz https://registry.npmmirror.com/hanzi-writer-data/-/hanzi-writer-data-2.0.1.tgz`（或 npm 官方 registry；raw.githubusercontent 直连在本机被重置）。
2. 解包到 `artifacts/stage2/src/package/`（artifacts 被 git 忽略，跨机迁移需单独复制）。
3. `python scripts/generate-stage2-fontpack.py` 重新生成字库包（脚本内含试点字表，断言每个字都有数据，缺字大声报错）。

## 7. 工程注意（实测踩坑，2026-10-06）

- **DCJS 不支持 Dictionary**：本机 .NET Framework 的 DataContractJsonSerializer 反序列化任何 JSON 对象键的 Dictionary（连 `Dictionary<string,double>` 都是）一律得到**空字典且无报错**。因此 fontpack 的 `glyphs` 必须是条目数组（`{"c":"字","strokes":[...]}`），字符作为字符串值传递；探针验证 `List<T>` 与嵌套 `List<List<double>>` 读取正常。加载器对此有注释，后人勿改回对象键。
- **PS 5.1 的 ANSI/GBK 陷阱**：无 BOM 的 .ps1 被按 GBK 误读；行尾中文字符的 UTF-8 末字节若落在 GBK 前导字节区（0x81-0xFE），会连同换行符一起被吞，**下一行代码被并进注释**（本次 `$wang` 定义行曾被吞导致测试假失败）。规矩：.ps1 一律纯 ASCII，中文字符用码点 `[char]0xXXXX` 构造，断言只匹配 ASCII 子串。
- GitHub raw 直连本机被重置，数据获取走 npmmirror 整包（见第 5 节）。
