## 1. 界面上有 6 个不同的「停」，不是一回事

入口都在主窗口左栏。前两个在「G 代码流」面板，后四个在「流量控制」面板。

| 入口                    | 控件               | 实际发出               | 层次   | 能恢复吗       |
| --------------------- | ---------------- | ------------------ | ---- | ---------- |
| 绿色 ▶ / ⏸（同一按钮，发送中变暂停） | `btnStreamStart` | `PauseStreaming()` | 软件流控 | 能（再点一次继续）  |
| 红色 ■                  | `btnStreamStop`  | `StopStreaming()`  | 软件流控 | **不能**     |

## 2. 逐个的源码语义

### 2.1 软件暂停 / 继续（`ControlSerialForm.PauseStreaming`）

**暂停请求时：**

- `isStreamingRequestPause = true`，`PreProcessStreaming()` 随即直接 return → **不再往控制板喂新行**。
- 但**已经排进控制板缓冲的整行会照常执行完**；要等控制板回到 IDLE 才真正切到暂停（`StreamingIDLE()`：`isStreamingPause = true`）。
- 切换瞬间记录 `posPause = posWork`，并发 `$G` 保存模态到 `parserStateGC`。

**关键推论**：暂停点由「最后一行已排出的代码」决定，**不由笔画边界决定**。

**排队量实测（2026-10-05 R2，见 5.2）**：按暂停的瞬间，PC 侧 `sendBuffer` 尚有 **10 行未确认**，控制板 `BFree 9/127`（RX 缓冲接近满）；按物理位置推算，机器当时还在画**第 2–3 个字**，而发送点已到**第 5 个字**——即「已发出但还没执行」的动作约有 **1~1.2 个字（约 15–17 个动作块）**，在 F200 下折合 **约 10 秒**运动。

所以暂停既有可能是「等很久才停」，也有可能停在某一笔的**绘制行末尾，此时笔仍处于下压（Z5）状态**。

**继续时：**

- 若 `posPause` 与当前 `posWork` 不相等（例如暂停期间有人手动移动过机器），走位置恢复分支：  
  `G90 G0 X.. Y..` → `G4 P0.5` → `G0 Z..`，最后重发 `parserStateGC`。
- 若位置一致，直接重发 `parserStateGC` 后继续喂行。

**风险点：**

1. 位置恢复的第一条是 **快速移动 `G0`，且发生在恢复 Z 之前** → 如果暂停期间挪动过机器/笔，恢复动作会**带笔横移**（拖线）。
2. 重发 `parserStateGC` 会把模态（含进给率）恢复成暂停时的值；代码对解析出的 `F0` 会替换为 `F100`。本机生成程序每行自带 `F`，影响有限，但需现场确认。
3. 暂停期间软件仍会继续应答/查询，不会自动抬笔。

**附带动作**：`flowControlEnable` 默认 **true**，`flowControlText` 默认 **`M5; M9`**。暂停或停止后会由主定时器延迟执行一次该文本。对 Z 笔机器无副作用（无主轴、无冷却）。

### 2.2 软件停止（`ControlSerialForm.StopStreaming`）

红色 ■ 走 `GuiControl.streamStop` → `MainFormUserControls.cs:249 StopStreaming(true)` → `ControlSerialForm.StopStreaming(isNotStartup:true)` → **直接 `StopStreamingFinal()`，不等 IDLE、也不向控制板发任何停机指令**（只发 `SendStreamEvent(GrblStreaming.stop)` 通知界面），然后 `ResetStreaming(true)` 清空软件侧 `streamingBuffer` 与 `sendBuffer`。

- **软件说停 ≠ 机器停**：控制板 RX 缓冲里已收到的行（实测约 10 行）与规划缓冲里的动作会**继续自己跑完**，这段时间界面已经显示为「已停止」。
- 只有错误/复位路径才走另一支：`StopStreaming(false)` → `isStreamingRequestStopp = true` + `isStreamingRequestPause = true`，**先等 IDLE**。
- **不可恢复**：缓冲已清空，不能接着画，只能重新发送。
- 同样**不抬笔、不回原点**。

### 2.3 进料保持 / 恢复（`!` / `~`）

- 实时字节，**不等 IDLE**：控制板立刻减速停止，**规划缓冲保留**。
- 点「恢复」`~` 后从原处继续，**不发生位置恢复、不重发模态** → 对连续笔控是当前最「干净」的暂停。
- 软件侧只更新状态显示（`GrblState.hold` → 高亮「恢复」按钮）。
- 保持期间供料仍在继续，直到把 127 字节填满为止，这是预期行为。
- 属于固件实时命令，软件流控状态机不参与，因此**不会清缓冲、不会打断本次发送**。

### 2.4 软复位（Ctrl-X）

界面上的「重置」有**两个入口，路径完全不同**（2026-10-05 R4 实测确认）：

- **流量控制面板的「重置」**：`UCFlowControl.BtnReset_Click` → `OnRaiseCmdEvent("", 0x18)` → `MainFormUserControls.OnRaiseCmdEvent` → `SendRealtimeCommand(0x18)` → `ControlSerialForm.RealtimeCommand(0x18)` → **只把一个字节写进串口**，并在 COM CNC 窗记 `> '0x18' Soft-Reset`。**不执行 `GrblReset`/`StateReset`、不 `SaveLastPos`、不刷新控件** → 软件完全不记账，事后只能靠"控制板自己发欢迎横幅"被动察觉。
- **COM CNC 窗口右下角的「重置」**（`btnGRBLReset`）：`GrblReset(true)` → `StateReset(true)`：`SaveLastPos()` 存档坐标 → `ResetVariables()`/`ResetStreaming()`/`mParserState.Reset()` → `UpdateControls()` → `JustgrblReset()` 发 Ctrl-X，COM CNC 窗记 `> [CTRL-X] reset`。

共同的结果：

- 立刻中断，**没有减速过程**；控制板清空规划缓冲与模态。GRBL 报 `ALARM:3 Reset while in motion. Machine position is likely lost` → **位置不可信**。
- 软件侧 `grblStateNow = unknown`、`mParserState.Reset()` → 软件对位置与模态的认知被重置，但固件步数位置仍然保留。
- 本机 `$20/$21/$22 = 0`：无软限位、无硬限位、无回零，**没有兜底**——报警后除了人工对位没有别的办法（`$H` 属项目禁令）。
- **不推荐**把它当「暂停」使用。
- ⚠️ **已知界面 bug**：复位/报警之后，**COM CNC 窗口的指令行与所有 `$` 按钮会被锁死**（少了两次 `UpdateControls()`）。成因与一键恢复见 5.6.1。

### 2.5 紧急报警（`$X`）

只解除报警状态，不产生任何运动。用于误触发 ALARM 后恢复操作。

## 3. 对连续笔控（本机 `requiresContinuousPenMotion = true`）的结论

1. **六种操作里没有一种会抬笔。** 若停在绘制行末尾，笔尖将压在纸上静止不动 → 渗墨、压痕、断墨；恢复后从断点续画会留下接头痕迹。
2. 软件暂停 / 软件停止**做不到「停在笔画边界」**：它们确实等到 IDLE，但 IDLE 可能正好落在某笔的绘制行末尾。
3. **「进料保持 `!` + 恢复 `~`」是当前唯一位置连续、无重新下降、无快速空移的暂停方式**——但笔仍然压着。若只是短暂停顿（几秒）影响最小。
4. 任何「暂停期间人工干预」（手动挪机器、手动抬笔改变 Z）都会让恢复逻辑进入位置恢复分支，可能**带笔横移**。
5. 停止 ■ 与软复位之后都**不能续画**，且都不回原点；实测端到端那次结束后机器停在末笔终点、由操作者手动回位，与此一致。

## 5. 现场测试与实测记录

### 前置条件（缺一不可）

1. 关闭原软件（奎享），COM9 空闲；用 `-Mode Normal` 启动本项目。
2. 笔已装好、纸已固定、笔尖当前离纸；实体急停放手边。
3. 发送前核对 G54、G92/TLO = 0、`$1 = 25`。**推荐用「机器控制 → 坐标系」窗口核对**：该窗口 `ControlCoordSystem` 在 Load 时调用 `RefreshValues(init:true)`，会**自动发送 `$#` 和 `$G`** 并把 G54–G59 / G28 / G30 / G92 / TLO 的数值全部列出，当前激活的坐标系高亮为绿色（`MarkActiveCoordSystem`）。开一个窗即可代替 COM CNC 指令行，无需键入任何命令。
   - 注意：AutoWriter 配置窗是 `ShowDialog`（模态），开着时会禁用主界面及其所有子窗口（含 COM CNC、坐标系）。正确顺序是**先在配置窗生成并载入预览 → 关配置窗 → 再开坐标系窗核对 → 再发送**；配置窗内的覆盖值/报告/预览在关闭后清空，但**程序已随「生成并载入主界面预览」进入主界面编辑器，不会丢**。
4. 测试程序用**内置 10mm「工」三笔**（生成并载入主界面预览）。
   - **注意（2026-10-05 20:34 实测确认）**：该程序只有 16 行有效 G 代码、约 198 字节，不到控制板 127 字节缓冲的 2 倍，因此**全部代码在开始后约 0.5 秒内就被喂入控制板**（日志 `snt:18` 已完成全部发送），之后控制板按绘制速度空跑约 3 秒。由此产生一个反直觉现象：
     - 「进料保持 `!`」「重置」「停止 ■」等**直接作用于控制板**的操作仍然有效，但按键窗口只有约 3 秒；
     - 「**软件暂停 ▶/⏸**」此时几乎无从生效（已无新行可拦），表现为「按了没反应、程序照常跑完、直接 `[Program end]`」——20:34 那次即为此现象，日志中只见 `pauseStreaming RequestPause Outstanding lines:2` 之后直接 `[Program end]` + `streaming finished ok True`，**没有**进入暂停态。
   - 要在软件暂停下观察到真实停顿，先把程序拉长：在「应用与写字预览」页&#x628A;**「绘图」显式覆盖降到约 200 mm/min**（同一段「工」可跑约 10 秒），或改用多笔画/多字程序。**每一轮只改一个变量。**
5. **每一轮只测一种停法**，不要混测；每轮结束记录后再开始下一轮。

### 5.5 R4 正式轮次：重置 / 软复位 Ctrl-X（2026-10-05 21:40 起，**已实测，结果见 5.6**）

**已核对的源码事实（决定本轮要看什么）**

1. 本轮按的是**流量控制**面板的「重置」：`UCFlowControl.BtnReset_Click` → `OnRaiseCmdEvent("", 0x18)` → `SendRealtimeCommand(0x18)` → `ControlSerialForm.RealtimeCommand(0x18)`——**只发 Ctrl-X 字节，不执行软件侧复位流程**。（原稿此处写成"→ `MainForm.BtnReset_Click()` → `GrblReset`"，2026-10-05 实测推翻，已改；那条链属于 **COM CNC 窗口**的「重置」。）

#### 5.1 「按钮无效」的根因：发送队列被堵死（**不是 grbl 拒收**）

⚠️ 最初曾判为「ALARM 锁定、grbl 拒绝除 `$X` 外的命令」——**方向对但机制错**。读 `bin\Debug\logfiles\logfile.txt` 后定位到真因。

**日志硬证据**（2026-10-06）：

```
01:32:52 ⚠ sendBuffer snt:0  cnfrmnd:1  cnt:10  BFree:127  lineNr:0  code:'$$'  state:alarm
01:35:00 ⚠ processGrblOkMessage  fix overflow  IndexSent:0  IndexConfirmed:1  Count:0
          （状态报告全程 <Alarm|...|Bf:15,128|...>）
```

队首那行 `$$` **一步都没发出去**（`snt:0`），后面 9 行全堵在队列里（`cnt:10`），且当时 `state:alarm`。

**两处成因，缺一不可**：

1. `ControlSerialFormInterface.cs` 的 `ProcessSend()` 约 1235-1239 行：

   ```csharp
   else if (line.StartsWith("$"))
   {
       if (!((grblStateNow == GrblState.idle) || (grblStateNow == GrblState.check)))
           break;      // 报警态下，所有 $ 命令一律不发
   }
   ```

   ⇒ 报警态任何 `$` 命令都**出不了串口**（不是被 grbl 拒收，是软件自己不发）。

2. `ProcessGrblWelcomeMessage()` 末尾**无条件**调用 `RequestSend("$10=2")` + `ReadSettings()`（发 `$$` / `$#`）。软复位后 grbl 正是 `ALARM:3`，这批命令一进队就永远发不出去 ⇒ **队列彻底堵死**，此后操作者点的任何命令都排在死行之后，全部表现为「无效」。

**为什么 `$X` 独活**：它在 `RequestSend()` 里被特殊处理成**旁路直发**（`SerialPortDataSend(tmp + lineEndTXgrbl)` 后直接 `return`），**不进 `sendBuffer`、不过 `ProcessSend` 的 Idle 闸门**。

**为什么不是「按钮没解锁」**：`UpdateControls()`（`ControlSerialForm.cs:1286-1295`）中 `cBCommand.Enabled` 与 `btnSend` / `btnGRBLCommand0..4` / `btnGRBLCmndParser` / `btnGRBLCmndBuild` / `btnCheckGRBL` **共用同一条件** `isConnected && (!isStreaming || isStreamingPause)` ⇒ 文本框能输入就说明按钮**必然同时是亮的**，「亮文本框 + 灰按钮」在代码上不可能并存。

#### 5.2 修复（候选 I-a，两处，均不改发送时序）

`ControlSerialFormInterface.cs`：

1. **不喂死队列**：`ProcessGrblWelcomeMessage()` 里若 `grblStateNow == GrblState.alarm`，**跳过** `$10=2` 与 `ReadSettings()`，并在 COM CNC 日志提示：

   > ⚠ 控制器处于报警状态：已跳过自动读取设置（报警时队列无法发出 $ 命令）。
   > 请先按 $X (Kill alarm lock) 解锁，再点「检查GRBL」读取设置。

   （已核实 `BtnCheckGRBL_Click` 在 Idle 且无缓存时会 `RequestSend("$$")`，这句提示是可执行的。）

2. **解锁即自愈**：`RequestSend()` 的 `$X` 分支在旁路直发**之前** `lock (sendDataLock) { sendBuffer.Clear(); }` —— 丢弃报警期间积压的死行，队列在解锁瞬间恢复。

## 7. 结论

- 离线语义：**已核实**。核心发现是「六种停法都不抬笔」，且软件暂停/停止的停止点不由笔画边界决定；`!` / `~` 是唯一位置连续的暂停。
- 实机：**R1 已完成并通过**（见 5.1）——`!` 使控制板真正进入 `hold`、无 `[Restore Position]`、位置连续、可续画、无丢步无报警；操作者目视「停住了 / 断点接着画 / 接头不明显」。按既定口径，**抬笔项为否（预期）**，故 R1 记为「位置与续画通过，抬笔否」。
- 实机：**R2 已完成、部分通过**（见 5.2）——⏸/继续机制成立（请求后立即停止喂行、恢复无 `[Restore Position]`、可续画、`ok True`），但**从按下到真正停住要等约 10 秒**（第 3 轮 11.42 秒），停点不由操作者决定；抬笔是偶然命中。**结论：⏸ 不能当急停，要立刻停只能用「进料保持 `!`」。**
- 实机：**R3（停止 ■）已完成（见 5.4）**——■ **不等 IDLE、不给控制板发停机指令**（推翻 §2.2 原文），属"软件放弃、机器照跑"：界面已显示"已停止"，机器仍继续画了约 2 个字 / 约 10.7 秒。**R3 未通过**（设计如此），价值是拿到这个可写进操作手册的数字。
- 实机：**R4（重置 Ctrl-X）已完成（见 5.6）——未通过**。硬停在约 1 秒内完成（比 ⏸ / ■ 快一个数量级，也正因此有丢步风险）；控制板报 `ALARM:3 Reset while in motion. Machine position is likely lost`，**位置确定丢失**，且本机无回零 → 只能人工对位；`Bf:15` 证明复位瞬间有在途指令被硬丢。**副作用：COM CNC 指令行会被锁死**（少了两次 `UpdateControls()`，上游 bug），一键恢复办法见 5.6.1。
- **四轮合起来的一句话**：界面上**只有「进料保持 `!`」是真正"立刻停、位置连续、可续画"的**；⏸ 要等约 10 秒且停点不可控，■ 和「重置」都不让机器立即停（■ 甚至不给控制板任何停机指令），「重置」还会丢位置、锁界面。
- 已由 20:34 日志**反证**一条：短程序（如内置 `工`）下**软件暂停无法产生可见停顿**，因为全部代码在 <1 秒内已喂给控制板；这属于「程序太短」而非功能故障。做软件暂停核实必须先拉长程序（降绘图速度或多笔画）。
- **R6 / 候选 K 实机触发验证已通过**（见 5.10，2026-10-06 09:20）：落笔停点 + 不动机器路径下，日志与纸面均确认 `[Restore Pen Z0->Z5 re-press]` 触发，恢复后第一笔（工3 顶横）完整，程序 line 35→83 全部完成。**R6 风险路径（暂停期手动移开 + 候选 K 的完整 Case A 序列）仍待装笔复测**——K 已加 Z 重压，但 XY 仍先于 Z 移动，**拖笔风险窗口未消除**。
- **R1 通过 + R6/K 实机验证不等于可以放心连续写**：抬笔仍做不到（候选 A 未实现），暂停期间人为移动机器的带笔横移风险（候选 B/D）仍未验证。
